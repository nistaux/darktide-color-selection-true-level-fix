# Color Selection – True Level Compatibility Fix

This directory is reserved for the new Darktide compatibility mod. Its intended DMF identifier is `color_selection_true_level_fix`.

Implementation is intentionally not scaffolded yet. The active design interview is settling the remaining parsing, performance, compatibility-detection, and validation boundaries.

## Accepted design contract

- The compatibility fix is a narrow adapter for the already demonstrated Color Selection nameplate fix, not a replacement or reimplementation of Color Selection. It does not provide Color Selection's settings, palettes, player-slot assignment, generalized coloring, or unrelated behavior.
- Color Selection owns the class-icon and player-name colors; True Level owns the character-level color, Havoc-rank color, and later inline formatting.
- The compatibility fix obtains the player-name color only from the leading inline color tag that Color Selection has already placed at the beginning of the Composed Nameplate's first line. Version one accepts exactly `{#color(R,G,B)}` with three no-space decimal integers from `0` through `255`; it does not generalize to RGBA, named, hexadecimal, or other color syntaxes. The compatibility fix never consults or recreates Color Selection's settings, account or slot assignment, or color-selection machinery. A missing, malformed, out-of-range, or newly unsupported leading color tag causes Safe No-Change pending compatibility review.
- From the end of that leading color tag through the end of the exact player-name segment, no additional inline formatting directive may occur. Version one detects an interruption conservatively: any additional literal `{#` sequence anywhere in that owned span causes Safe No-Change with `owned_span_formatting_interrupted`, without parsing or classifying the directive. The compatibility fix otherwise treats the class-icon prefix as opaque and does not recreate it. It maintains no allowlist of directive types and does not log the directive text.
- A successful Color-Boundary Splice changes only the color boundary immediately after the exact player-name segment: it inserts the fixed, case-sensitive ten-byte literal `{#reset()}` there without replacing any existing byte and preserves every existing character and inline-formatting tag after that point exactly as received. When the name ends at the first-line boundary, the reset is inserted immediately before the existing `\n`; when the name ends the string, the reset is appended. Version one does not emit a parameterized, case-folded, or alternate reset form. It does not choose or calculate a color. If the splice would require deleting, rebuilding, or interpreting True Level's suffix, the compatibility fix uses Safe No-Change. The literal follows canonical current Darktide source usage and remains a patch-sensitive assumption requiring static review and in-game confirmation on both Supported Surfaces after relevant game updates.
- The accepted Activation Condition and structural safety checks are sufficient to permit that splice; the compatibility fix does not require a recognizable True Level string signature on each nameplate. Valid suffixes may be colored, plain, indistinguishable from the base level display, or empty. Everything after the exact player-name segment remains opaque.
- The compatibility fix does not inspect True Level's private `marker.tl_modified` field or any equivalent private per-marker flag. Such a flag neither proves a visible suffix exists nor provides a stable cross-mod contract.
- If the exact literal `{#reset()}` is already positioned immediately after the exact player-name segment, the result is Already Compatible: the entire Composed Nameplate remains unchanged, no duplicate reset is inserted, and no Compatibility Diagnostic is emitted. Other reset-like syntax does not qualify.
- If the exact player-name segment cannot be identified confidently, the compatibility fix leaves the Composed Nameplate unchanged.
- The intended integration seam is a DMF `hook_safe` on `HudElementNameplates.update`, first attempted during `on_all_mods_loaded` so it post-processes the Composed Nameplate after both Dependency Mods have contributed. Registration is permitted only against the actual class table and callable `update` method; the compatibility fix never enters DMF's string-target delayed-hook queue. Current Dependency Mod versions register their safe hooks during ordinary script loading, so direct later registration preserves their callback order. This ordering remains an explicit compatibility assumption requiring static review and in-game validation after relevant updates. If the direct target is unavailable during `on_all_mods_loaded`, or the initial `hook_safe` call throws, that initial failure is silent and registration is attempted once on every `on_game_state_changed("enter", "StateGameplay")` event until it succeeds. Target unavailability at gameplay entry emits `hook_target_unavailable`; a `hook_safe` exception at gameplay entry emits `hook_registration_failed`. Both are default-log-only Compatibility Diagnostics emitted once for that World Visit. A registration attempt succeeds only when `hook_safe` returns normally. After success, the hook remains registered exactly once and no further registration attempts or hook-registration diagnostics occur.
- The compatibility fix will not wrap or replace either Dependency Mod's formatting functions and will not require a special user-managed load order merely to run after their nameplate hooks.
- The clean player-name comparison value comes from `marker.data:profile().name` with nil and type guards. A usable name is a Lua string with byte length greater than zero and is used exactly as returned, with no trimming, normalization, or case conversion. A `nil`, non-string, or empty name causes Safe No-Change with `profile_name_unavailable` and `profile_stage = name_value`. The compatibility fix does not attempt to recover that value by stripping markup from Color Selection's hooked `player:name()` result. Nonmatching profile-name data causes Safe No-Change. Because marker and profile fields are patch-sensitive game internals, local and remote nameplates require in-game validation after relevant updates.
- Player-name matching is confined to the portion of the Composed Nameplate after the validated leading color tag and before the first literal line-feed byte `\n`, or through the end of the string when no `\n` exists. No carriage-return or Unicode line-separator normalization is performed. The leading tag itself and all later lines, including an optional title line, are excluded from matching; later lines are preserved unchanged. If a future layout moves the player name outside this region, the compatibility fix uses Safe No-Change pending compatibility review.
- Within that search region, the clean profile name must occur exactly once as a case-sensitive literal string. Overlapping literal matches count as separate occurrences: after the first match, ambiguity detection searches again beginning one byte after that match's start rather than after its end. Zero or multiple occurrences cause Safe No-Change; approximate, case-folded, normalized, and Lua-pattern matching are not used.
- The complete profile name is located before any post-name boundary is examined. The compatibility fix never splits the Composed Nameplate on a hyphen or on the literal suffix delimiter ` - `. After the exact full-name match ends, a nameplate that is not Already Compatible is eligible only when the next bytes are the current ` - ` suffix delimiter or the end of the first line; any other continuation causes Safe No-Change. Hyphens and delimiter-like text inside the matched player name remain ordinary name characters.
- The compatibility fix iterates only `HudElementNameplates._nameplate_units`, resolves those entries to their world markers, requires a marker type containing the literal `nameplate`, and rejects any marker type containing `companion`. It does not scan every world marker, hardcode the mission-only `nameplate_party` type, or implement a companion branch. The collections, marker identifiers and types, and widget fields are patch-sensitive game internals requiring mission and Mourningstar validation.
- Unresolved or disappearing individual markers and unfinished widgets are normal lifecycle conditions and are skipped silently. For a resolved candidate, a missing, `nil`, or empty header is also a silent lifecycle skip; a non-empty string proceeds to the Color-Boundary Splice core. A present but non-string header causes Safe No-Change with `composed_nameplate_unusable`. When the Activation Condition is true, an expected top-level nameplate or world-marker collection that exists in a wrong or structurally unusable type causes Safe No-Change and its one-per-World-Visit Compatibility Diagnostic.
- Each candidate player nameplate is processed in isolation. The complete replacement string is validated and built locally, then assigned once only after every check succeeds. An unexpected error leaves that candidate unchanged, emits the applicable one-per-World-Visit Compatibility Diagnostic, and does not prevent processing other candidates.
- Unexpected processing errors are converted into a stable Diagnostic Reason Code plus an allowlisted fixed processing-stage value. Built-in diagnostics do not include raw exception text or stack traces.
- Diagnostic Reason Codes are action-oriented: conditions receive different codes only when they lead to materially different maintenance checks. Minor syntax or runtime variants with the same next action share a code rather than creating additional per-World-Visit log entries.
- The compatibility fix evaluates the Activation Condition through DMF's public `get_mod`, `is_enabled`, and namespaced `get` primitives using the exact identifiers `ColorSelection`, `true_level`, and `enable_nameplate`. It does not call True Level's private feature helper. A missing mod or method, an evaluation error, `nil`, or a non-boolean feature value means inactive. The user-facing `enable_nameplate` setting identifier remains a patch-sensitive compatibility assumption that requires review after relevant True Level updates.
- The Activation Condition is evaluated once at the start of every post-update hook invocation and is not cached across frames or World Visits. If inactive or indeterminate, the callback returns before inspecting any nameplate; no polling timer is used.
- While active, version one reevaluates each current candidate from `_nameplate_units` on every hooked `update` invocation and keeps no per-nameplate splice-result cache. A successful replacement is assigned once; subsequent unchanged frames are recognized as Already Compatible and perform no assignment. Fresh evaluation avoids stale decisions when markers are reused, profile or suffix content changes, or another contributor rewrites the Composed Nameplate.
- Missing or disabled Dependency Mods and an explicit `enable_nameplate == false` are expected inactive states and remain silent. If the Dependency Mods are present but an expected DMF method errors, the True Level setting is unexpectedly unavailable, or its value is non-boolean, the compatibility fix uses Safe No-Change and emits the applicable one-per-World-Visit Compatibility Diagnostic.
- Version one supports player world nameplates in missions and the Mourningstar. Team HUD panels and other views remain unverified and out of scope until separately researched and validated.
- The first occurrence of every recognized, coded Safe No-Change cause emits one Compatibility Diagnostic per World Visit through DMF's default-log-only information channel; later occurrences of that cause are suppressed until the next World Visit, with no deliberate chat message or notification. A World Visit is one continuous stay in a loaded world and resets at each world transition, including a return to a surface visited earlier during the same launched game. A distinct cause is identified solely by its stable Diagnostic Reason Code, regardless of differing structural metadata or whether it occurred in a mission or the Mourningstar. Each code describes the condition directly observed by the compatibility fix without attributing fault to either Dependency Mod. Published codes retain their meanings across releases; newly distinguished conditions receive new codes. Each code has its own allowlist of relevant, non-identifying structural metadata; available runtime context is never dumped automatically. Diagnostics omit the raw Composed Nameplate, player names, account IDs, and other identifying values. Version one provides no opt-in verbose mode that logs those omitted values.
- Every Diagnostic Reason Code may include `first_observed_surface` metadata when known. Its value identifies only where that World Visit's one-time diagnostic first occurred, not every surface affected by the cause.
- Every Diagnostic Reason Code may include the installed version identifiers of Color Selection – True Level Compatibility Fix, Color Selection, and True Level when those identifiers are available through stable public interfaces. A version that cannot be obtained that way is recorded as `unavailable`; diagnostics do not use private APIs or alter compatibility behavior merely to obtain it.
- Version one does not use runtime version allowlists or blocklists for Color Selection or True Level. Runtime compatibility behavior is governed by the accepted structural checks and Safe No-Change rules; available installed versions provide diagnostic and validation context but never activate, deactivate, or otherwise alter the Color-Boundary Splice. Repository documentation records each Validated Version Combination. A combination absent from that record is not automatically rejected at runtime, but it is not represented as validated.
- Deterministic Color-Boundary Splice, activation, diagnostic, and suppression branches are covered by table-driven static tests using synthetic, non-identifying inputs and lifecycle sequences. These tests cover exact `{#reset()}` insertion and Already Compatible detection, rejected reset-like variants, accepted and rejected leading tags, exact-name matching and ambiguity, hyphens and delimiter-like text inside names, owned-span formatting interruptions, accepted and unexpected post-name boundaries, opaque suffix preservation, successful replacement, Safe No-Change, missing and disabled Dependency Mods, invalid activation states, diagnostic classification, one-per-reason suppression within a World Visit, and reset before retry on gameplay entry. In-game validation focuses on the real game and Dependency Mod seams: hook registration and order, actual nameplate structures and rendering, activation changes, real World Visit entry events, continued processing, and surface transitions. Validation does not force malformed private runtime state merely to reproduce every statically testable branch. If a real Safe No-Change diagnostic occurs naturally, its suppression and reset behavior is recorded as additional evidence but is not mandatory for a Validated Version Combination. Offline tests use 64-bit LuaJIT 2.1 from the MSYS2 UCRT64 `mingw-w64-ucrt-x86_64-luajit` package, without a third-party test framework. Shared source stays within the conservative Lua 5.1 subset, returns a plain module table, performs no load-time access to Darktide or DMF globals, and receives required data or services as arguments. The in-game wrapper loads it through `mod:io_dofile`; the offline runner loads the same source through `dofile`. The canonical repository-root command is `luajit color_selection_true_level_fix/tests/run.lua`; the runner prints a concise pass/fail summary and exits nonzero when any case fails. Every validation entry records the exact LuaJIT package version used. Installation or provisioning requires Austin's explicit approval and has not occurred.
- The future Color-Boundary Splice core is an ordinary pure Lua module that receives only a Composed Nameplate string and clean profile-name string, then returns an explicit `splice`, `already_compatible`, or `safe_no_change` outcome and returns a complete replacement string only for `splice`. A `safe_no_change` result also returns the stable Diagnostic Reason Code and any reason-specific allowlisted structural metadata for the condition detected by the core; it never logs. `splice` and `already_compatible` return no diagnostic reason. It does not access Darktide, DMF, widgets, markers, either Dependency Mod, mutable runtime state, or logging. The game-facing adapter obtains and validates runtime data, isolates candidates, invokes the core, classifies adapter-only failures, assigns a successful replacement once, and exclusively owns diagnostic emission and per-World-Visit suppression. The same core code is exercised by the offline static tests and by the in-game adapter; offline success does not replace live integration validation.
- The core validates in a fixed dependency order and the first failing check determines the `safe_no_change` reason: validate the exact leading color tag syntax and RGB range; establish the first-line search region; require exactly one literal profile-name match; reject any additional `{#` in the owned span; classify the immediate post-name boundary as Already Compatible, splice-eligible, or unusable; and build the replacement only after every prior check passes. This precedence is deterministic and is part of the table-driven test contract.
- `color_selection_true_level_fix/VALIDATION.md` is the canonical evidence ledger for Validated Version Combinations and will be created only when the first real validation run produces a record. The mod README remains the design and behavior contract and will link to that ledger once it exists. Each ledger entry records the exact three-mod version tuple, the exact Darktide build, DML version, and DMF version as required environment context, the checks performed, results, date, and remaining limitations; design or scaffolding alone never creates a validation entry. The environment identifiers provide reproducibility context but do not become part of the canonical three-mod combination identity. All three mod version identifiers and all three environment identifiers must be available before a run can be recorded as a Validated Version Combination. A run with any unavailable required identifier may be retained as incomplete validation evidence but does not enter the validated-combination ledger. The validation claim applies only to the exact recorded environment: any Darktide, DML, or DMF version change requires a new passing entry even when the three mod versions are unchanged, and an older entry remains historical evidence only. The ledger may therefore contain multiple environment-specific entries for the same three-mod tuple. Each entry derives its checklist from every compatibility assumption that this contract marks as patch-sensitive or requiring validation, classifying each item as static review, in-game validation, or both. Every applicable item must have a recorded passing result; a failed, skipped, or uncheckable item leaves the run incomplete. Complete in-game validation requires passing checks in both a mission and the Mourningstar within the recorded environment; missing or failing either Supported Surface leaves the run incomplete. On each surface, the mandatory positive case observes at least one remote player nameplate and confirms that Color Selection's class-icon and exact player-name coloring remain intact, the Color-Boundary Splice ends that leading color exactly after the full player name, and True Level's character-level color, Havoc-rank color, and later inline formatting remain intact. The ledger records the result; screenshots or notes may support but do not replace the pass/fail record. If the current runtime exposes a local player world-nameplate candidate on either Supported Surface, each exposed local case must pass the same ownership and splice checks. If neither surface exposes a local candidate, the ledger may mark local coverage `not applicable` with the observed reason; this is distinct from skipping or failing to test an applicable case. Validation does not add private instrumentation or fabricate a marker solely to force local coverage. Every complete run also includes one continuous `Mourningstar -> mission -> Mourningstar` sequence in the same launched game and confirms that each gameplay entry begins a new World Visit, the hook remains registered exactly once, and nameplate processing resumes on return without re-registration. Offline lifecycle tests prove suppression reset ordering; a naturally occurring live diagnostic may add but is not required evidence. On one Supported Surface, every complete run toggles True Level's `enable_nameplate` setting from `true` to `false` and back to `true`, confirming immediate silent inactivity while false and resumed processing while true without restart or hook re-registration; this validates that the setting state is not cached across hook invocations. Separate live runs with either Dependency Mod disabled or absent are not required for a Validated Version Combination; the expected-inactive branches are covered by offline adapter tests instead. Every complete run also performs a qualitative performance smoke check in a populated mission and Mourningstar for obvious stutter, repeated assignments, or log spam. Version one has no numeric frame-time threshold until a repeatable benchmark method exists; any observed performance problem requires profiling and resolution before validation can pass.
- Hashes, fingerprints, and other transformed values derived from the raw Composed Nameplate, player names, account IDs, or other identifying text remain identifying and are prohibited from built-in diagnostics. Structural classifications are permitted only when they are derived from non-identifying features and use a fixed, documented, human-readable vocabulary rather than generated signatures or serialized structures.
- Each World Visit begins, and diagnostic suppression resets, on DMF's public `on_game_state_changed("enter", "StateGameplay")` event. The handler begins the new World Visit and resets suppression before attempting any pending direct hook registration, so a failed retry is recorded against the newly entered visit. Suppression is not reset on exit. In-game validation must confirm the event sequence for Mourningstar-to-mission-to-Mourningstar transitions. Validation does not deliberately disconnect from an active mission or induce error-recovery failures; reconnect and error-recovery paths are evaluated and recorded if they occur naturally and otherwise remain explicit unvalidated limitations without blocking a Validated Version Combination.

## Accepted diagnostic catalog

- `hook_target_unavailable`: The actual `HudElementNameplates` class table or its callable `update` method remained unavailable when direct registration was attempted at gameplay entry. The earlier `on_all_mods_loaded` miss is silent. Permitted reason-specific metadata is `target_stage`, using only `class_table` or `update_method`. Raw target values are excluded.
- `hook_registration_failed`: The actual direct target passed validation, but the `hook_safe` registration call threw during a gameplay-entry attempt. The earlier `on_all_mods_loaded` failure is silent. No reason-specific metadata is recorded; raw exceptions and tracebacks are excluded.
- `activation_state_unreadable`: The Activation Condition could not be evaluated because an expected activation integration returned an error or an invalid state. Permitted reason-specific metadata is `activation_stage`, using only `color_selection_state`, `true_level_state`, or `nameplate_setting`. Returned values and raw errors are excluded.
- `nameplate_structure_unusable`: An expected top-level nameplate structure exists in an unusable form while the Activation Condition is true. Permitted reason-specific metadata is `structure_stage`, using only `nameplate_units` or `world_marker_map`. Normal unresolved individual markers and unfinished widgets do not produce this diagnostic.
- `composed_nameplate_unusable`: A resolved candidate exposed a present, non-string header value. No reason-specific metadata is recorded; the value and its serialized or transformed forms are excluded. Missing, `nil`, and empty headers remain normal silent lifecycle skips.
- `profile_name_unavailable`: A resolved player candidate did not provide a usable clean profile name. Permitted reason-specific metadata is `profile_stage`, using only `profile_accessor`, `profile_record`, or `name_value`. Player data that has not resolved yet is a normal silent skip; profile contents and returned values are excluded.
- `profile_name_not_found`: The clean profile name had zero exact, case-sensitive literal occurrences in the Composed Nameplate's first line. No reason-specific metadata is recorded.
- `profile_name_ambiguous`: The clean profile name had multiple exact, case-sensitive literal occurrences in the Composed Nameplate's first line. No reason-specific metadata is recorded; the name, match positions, surrounding text, and occurrence count are excluded.
- `leading_color_tag_unusable`: The expected leading `{#color(R,G,B)}` tag was absent, malformed, or contained an out-of-range component. Permitted reason-specific metadata is `tag_stage`, using only `missing`, `syntax`, or `range`. The raw tag and RGB values are excluded.
- `owned_span_formatting_interrupted`: An additional literal `{#` sequence occurred between the end of the leading Color Selection tag and the end of the exact player-name segment. No reason-specific metadata is recorded; the directive or literal text and surrounding content are excluded.
- `post_name_boundary_unusable`: The bytes immediately after the exact player-name segment were neither the exact `{#reset()}` literal for Already Compatible, the accepted ` - ` suffix delimiter, nor the end of the first line. No reason-specific metadata is recorded; alternate reset-like syntax, continuation bytes, and surrounding text are excluded.
- `candidate_processing_exception`: An unexpected exception interrupted an isolated candidate operation. Permitted reason-specific metadata is `processing_stage`, using only `profile_lookup`, `structure_validation`, `replacement_build`, or `assignment`. Raw exceptions, tracebacks, runtime values, and nameplate content are excluded.

These are the settled version-one design decisions, not implemented behavior. Austin confirmed shared understanding on 2026-07-15. Scaffolding, implementation, LuaJIT provisioning, and in-game changes require a separate explicit request; the accepted static and live validation contract applies once implementation exists.
